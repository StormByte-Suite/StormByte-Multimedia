# Synthetic media fixtures

Video and audio payloads are synthetic seeded noise, approximately two seconds per clip unless stated otherwise. Subtitle cues are synthetic text. Images are synthetic noise. The redistributed font has its own license notice. Fixed fixtures must not be regenerated by tests.

## Video

- `video/bluray_like_hdr10.mkv`: HEVC Main 10, BT.2020/PQ, mastering-display and content-light metadata; English AC-3 5.1 and Spanish AAC 5.1; English and Spanish PGS; attached synthetic cover.
- `video/bluray_like_hdr10.mp4`: H.264 8-bit SDR video with a BT.709 color matrix, two 5.1 AAC tracks and English/Spanish `mov_text` subtitles. Primaries and transfer are unspecified; HDR metadata is absent.
- `video/bluray_like_vp9.mkv`: VP9 video, the same two distinct 5.1 audio codecs and English/Spanish PGS subtitles.
- `video/anime_like.mkv`: one HEVC video, one English Opus 5.1 track, three bitmap PGS tracks (`spa`, `eng`, `jpn`) and one `ipag-mona.ttf` attachment.
- `video/hdr10_metadata_source.mkv`: HEVC Main 10 source with BT.2020/PQ, mastering-display and content-light metadata.
- `video/hdr_without_mastering_metadata.mkv`: BT.2020/PQ HEVC Main 10 with mastering-display and content-light side-data intentionally absent. `File` is expected to classify it as HDR10-like and report `HDR10::Source::Heuristics` from the signaled primaries/transfer, rather than treating it as SDR.
- `video/xvid_mp3_stereo.avi`: Xvid/MPEG-4 Part 2 video with stereo MP3 audio.
- `video/interleave_long.mkv`: twelve seconds, longer than any encoder lookahead the interleave tests configure, so a video encoder lagging audio by seconds shows up in file order. H.264 High 320x180 at 24000/1001 fps from the `testsrc2` pattern, GOP 24 with three B-frames; English AC-3 stereo pink noise, seed `20261026`. Authored with FFmpeg 9.0.2 on 2026-10-26. SHA-256: `7ed06e6575e3794c94e4a8e1a69fe6b002962ccde00c7d2414b0df888f5e08af` (327,078 bytes).

  ```sh
  ffmpeg -hide_banner -loglevel error -n \
    -f lavfi -i 'testsrc2=size=320x180:rate=24000/1001:duration=12' \
    -f lavfi -i 'anoisesrc=color=pink:amplitude=0.1:sample_rate=48000:duration=12:seed=20261026' \
    -map 0:v -map 1:a -c:v libx264 -preset veryslow -crf 30 -g 24 -bf 3 -pix_fmt yuv420p \
    -c:a ac3 -b:a 96k -ac 2 -metadata:s:a:0 language=eng \
    -fflags +bitexact -flags:v +bitexact -flags:a +bitexact interleave_long.mkv
  ```

### Dolby Vision

- `video/dovi_only.mkv`: synthetic Profile 5, compatibility ID 0; IPT-PQ-C2 matrix, full range, BT.2020 primaries and PQ transfer are explicitly signaled. It has no static HDR10 mastering-display/content-light SEI or HDR10-compatible VUI; DOVI RPU Level 6 metadata is present.
- `video/dovi_hdr10.mkv`: synthetic Profile 8, compatibility ID 1; explicit HDR10 mastering-display/content-light metadata and BT.2020/PQ signaling.

Both fixtures contain one HEVC Main 10 stream, 320x192, 24 fps, 48 frames and two seconds of deterministic noise with seed `424242`. Dolby Vision configuration: version 1.0, level 1, compression 0, RPU present, enhancement layer absent and base layer present. Every decoded frame carries raw RPU and decoded Dolby Vision metadata.

The combined fixture has mastering-display primaries G(13250,34500), B(7500,3000), R(34000,16000) and white point WP(15635,16450), with chromaticity denominator 50000; maximum/minimum luminance 4000/0.005 nits; MaxCLL 636 and MaxFALL 103. `File` exposes stream configuration; decoded pipeline frames additionally expose parsed metadata and owned RPU bytes.

### HDR10+

- `video/hdr10plus_metadata_source.mkv`: fixed synthetic HEVC Main 10 source, 1920x1080, `yuv420p10le`, 24 fps, 48 frames and two seconds, with BT.2020 primaries, BT.2020 NCL matrix and PQ transfer. It combines the existing `hdr10_metadata_source.mkv` picture source with registered SMPTE ST 2094-40 dynamic metadata; it is not calibrated HDR content.
- `video/hdr10plus_metadata.json`: the retained authoring metadata, HDR10+ profile A, JSON version 1.0, application version 1, one window and 48 frame entries. Two distinct payloads alternate on successive frames: targeted display luminance 400/600 nits, different MaxSCL, average/percentile distributions, knee points and four Bezier anchors. Tests construct these expected values in-process, without a JSON reader or authoring-tool dependency.

Static mastering metadata: G(13250,34500), B(7500,3000), R(34000,16000), WP(15635,16450), denominator 50000; maximum/minimum luminance 1000/0.005 nits; MaxCLL 1000 and MaxFALL 400. A one-off `ffprobe` validation on 2026-10-12 found 48 decoded frames, each carrying mastering-display, content-light and HDR10+ side data. Strict `hdr10plus_tool` extraction checks the registered HEVC SEI against the retained JSON. These tools are fixture-authoring/validation tools only, never repository test dependencies; tests do not regenerate either file.

The in-process HDR10+ suite checks public `File` detection against the static-only fixture, registry capabilities, Matroska remux, x265 HEVC, libaom AV1 and both native/libvpx VP9 decoders. Every hop compares all 48 normalized T.35 payloads, monotonic 24 fps timestamps within Matroska's 1 ms rounding, color properties and static HDR10, allowing only AV1 static-metadata quantization. The HEVC -> AV1 -> HEVC case also remuxes final HEVC to an elementary stream and requires native decoded `AVFrame` HDR10+ side data on every frame, proving registered SEI preservation independently of Matroska BlockAdditions. Raw-stream decoding is compared in display order, without a container timestamp requirement. VP9 support is limited to the existing Matroska ITU-T T.35 BlockAddition route, not invented VP9 bitstream metadata.

## Subtitles

- `subtitles/*.sup`: genuine HDMV PGS bitmap tracks in SUP format; the anime-like set includes Spanish, English and Japanese.
- `subtitles/*.srt`: matching synthetic text cues, except for the independent late-cue regression below.
- `subtitles/late_first_cue.srt`: original synthetic SubRip text containing one cue from `01:00:00,000` to `01:00:02,000`. It exercises a subtitle track whose first cue is timestamped one hour after the start. Reading the fixture does not wait in real time; the test encodes it as ASS in Matroska through `Transcoder` and inspects the output with `File`.
The Japanese PGS was rendered with `IPAMonaGothic` at a larger size for OCR coverage. The test transcodes it to SubRip using the bundled `jpn.traineddata` and checks for the hardcoded Japanese tokens `字幕` and `出発` in the resulting Matroska subtitle packet.

## Test-generated outputs

Generated media is written under the configured `STORMBYTE_TEST_OUTPUT_DIR`, normally `<build>/test-output`, under
`<executable>/<test-case>/`. These outputs are not additional redistributed fixtures. Codec roundtrips generate their
intermediate inputs within the same case and do not depend on execution order.

- `pipeline/audio-codecs/`: stereo PCM, surround AAC and Opus fixtures exercise FDK-AAC, Vorbis, Opus, LAME, FLAC, ALAC and AC-3/E-AC3. The cases inspect container and codec identities, channel count, 48 kHz sample rate and positive duration. FDK-AAC is required when FFmpeg is bundled with nonfree enabled.
- Tagged-audio cases independently convert both `audio/noise_tagged.mp3` and `audio/noise_tagged.opus` to Vorbis/Ogg, Opus, native FLAC, ALAC/M4A, AAC/M4A and MP3, then reopen each output through public `File::Metadata()` and assert all ten placeholder fields and the absence of copyright. MP3-to-MP3 and Opus-to-Opus explicitly select encoders and recode; Opus-to-MP3 explicitly selects `libmp3lame`. The MP3 fixture also roundtrips through Vorbis and Opus back to MP3, exercising metadata read from stream comments and written back as ID3. Separate MP3-to-MP3 and Opus-to-Opus remux cases call `Remux()` without an encoder and preserve the same fields. An untagged WAV-to-Opus case must not invent music tags. Tests compare semantic values, not ID3 bytes: Vorbis/Opus/FLAC use Vorbis comments and M4A uses MP4 metadata. Optional encoder availability follows the existing codec test skip policy.
- `pipeline/video-codecs/`: the H.264 SDR MP4 fixture is scaled to 320x192 for SVT/libaom AV1, VP8/VP9, x264, OpenH264, Kvazaar and x265. AV1 decoder cases generate their own input before selecting dav1d or libaom. The scaled dimensions are multiples of eight for Kvazaar compatibility.
- `pipeline/mux-policy/`: the stereo PCM fixture produces direct FLAC, FLAC in OGA, ALAC in CAF and direct E-AC3. Negative cases cover incompatible codec/container combinations and WebM attachment rejection.
- `pipeline/mp4-policy/`: the five-track H.264/AAC/timed-text MP4 fixture exercises individual and mixed outputs, two audio or subtitle tracks, reversed audio order, all five tracks, `.m4a`/`.m4b` aliases and mixed remux/encode. The HEVC MKV supplies a HEVC/AAC remux case. Its synthetic PNG cover is preserved byte-for-byte in video MP4 and audio-only M4A as cover art, and in Matroska as a real attachment. `File` must expose each cover through `Attachments()` without adding a playable video stream. Matroska additionally preserves the original filename. The IPA Mona font exercises explicit rejection of resources that the MP4 backend cannot represent; this is an implementation limit, not a claim that ISO BMFF forbids embedded resources. Successful outputs are checked for track count, order, codec, language, dimensions, audio properties and duration.
- `pipeline/subtitle-header/`: manual pipelines use the existing MKV and MP4 fixtures as audio sources while reserving ASS or MOV timed-text encoders. Input subtitles are decoded and passed through a test filter that removes their payload before reaching the encoder; all queues have consumers and EOF propagates normally, but no output cues are generated. These cases check that codec preparation does not wait for a first cue and that Matroska retains the selected empty subtitle track. MP4 may omit a track that finishes entirely empty, as libavformat does; the test does not require an artificial empty final track. `late_first_cue.srt` separately exercises encoding of a real cue at one hour, including decoder initialization after the short source reaches EOF.
- `pipeline/watermark/`: path and embedded-byte variants use the same colored-noise logo and distinct output filenames. Both outputs are 640x360 VP9 WebM. `File` checks container, codec, resolution and positive duration; overlay appearance is checked manually.
- `pipeline/dovi/`: DOVI-only, HDR10-only and combined cases each produce separate Matroska remux, libx265 reencode, watermark and pixel-replacement outputs. The `-verified.mkv` copies reopen the written outputs through public remux/analytics APIs to decode them again. Tests compare configuration, color properties, static HDR10 fields, decoded DOVI fields, exact per-frame RPU bytes and frame counts. DOVI inputs must yield 48 frames. Copy/move and owned-RPU loader cases additionally check public value/frame preservation. VP9 and Kvazaar cases require explicit DOVI rejection, not successful metadata loss.

Dolby Vision fixtures are not visually calibrated or Dolby-certified content. DOVI/HDR watermark regressions retain source dimensions and color properties and check metadata preservation, not overlay appearance or Dolby calibration. RPU spatial assumptions may become inconsistent after cropping, aggressive scaling or color transformations.

Tests use StormByte public APIs; no external media programs or libdovi are required. Optional implementations may be skipped only when unavailable; actual encoding failures are not successful skips. Bundled GPL-disabled configurations omit the x265/Kvazaar cases.
